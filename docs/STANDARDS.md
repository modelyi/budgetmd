# 项目文档与交付物管理标准

本文件确立项目文档与交付物的统一管理标准：T5 专项方案管理标准（第一节～第四节、第七节）、交付物排版映射协议（第五节）、方案与需求规格编写标准（第六节）、财务合规与准则审核要求（第六、七节）。方案文档与页面实现、脚本实现冲突时，一律以本文件为准。

## 一、基准源：纯 Markdown 文件

1. T5 专项方案一律以**纯 Markdown 文件为基准源**，存放于：
   - 多方案集合：`docs/solutions/*.md`；
   - 单篇方案：`docs/*.md`。
2. 一篇方案一个 `.md` 文件；文件名用业务语义命名（示例：`docs/solutions/AA-内部关联交易方案.md`《集团内部关联交易方案》）。
3. 正文使用标准 Markdown（标题、段落、列表、表格）；关系示意可用 Mermaid 或静态图，图的含义以随文文字说明为准。
4. 页面（T5 页签）只做 Markdown 文件的读取与展示；内容改动一律直接落回 Markdown 文件。

## 二、禁止事项

1. **严禁依赖前端 localStorage（浏览器本地缓存）存储业务方案内容。** 方案正文只认磁盘上的 Markdown 文件；浏览器缓存只能是无落盘的临时草稿，不得作为交付、复核、引用的依据。
2. **严禁过度工程化包装。** 不得把方案正文拆散为自定义嵌套组件（卡片网格、条目、提醒块之类的结构树），也不得在 Markdown 之外另立并行的正文数据源（TS 常量、JSON 分片等）。

## 三、人工干预规范

1. 人工干预直接面向纯 Markdown 文件：定位对应 `.md`，直接改文字、保存即完成；不依赖页面操作或生成脚本。
2. 业务语言平实：谁、什么业务、填哪张表、走什么口径、出哪张报表，直接写清楚；严禁 AI 腔调与假大空套话（如堆砌「赋能」「闭环」「生态」「全面提升」之类空词）。
3. 口径表述与全库既定口径一致；报表项仅允许在标准报表项后追加「—内部往来」后缀（如「营业收入—内部往来」「其他应付款—内部往来」），科目颗粒度止于报表项目行。

## 四、关联交易场景标准术语

关联交易场景统一使用下列法定标准术语，不得以自造简称或临时别名替代：

| 标准术语 | 说明 |
| :--- | :--- |
| 原材料代采购 | 代采购服务提供方统一对外采购原材料、备件，按需调拨给各制造基地 |
| 设备代采购 | 代采购服务提供方对外采购机台仪器，调配给使用基地 |
| 内部产品销售 | A 卖自产产成品给 B，B 作半成品/原材料再加工后对外销售 |
| 内部物料销售 | A 卖物料给 B 的对客技术服务项目，真实购销、加成进成本 |
| 内部人工销售 | A 派人工服务给 B 的对客项目，真实服务购销、加成进成本 |
| 内部职场租赁 | 物业持有公司出租厂房、办公区或工位给子公司 |
| 内部资金借贷 | 集团资金中心与子公司之间的短期资金拆借 |
| 二手资产转卖 | 子公司之间调配转让已有折旧的旧设备/无形资产 |
| 代采购服务提供方 | 承担对外统一采购、按需调拨职能的一方；口径归集到下单主体（管理单元）关联的法人公司 |

## 五、交付物排版映射协议

按交付物类型套用下列固定排版模式，禁止混用或自创版式：

| 交付物类型 | 排版模式 | 要点 |
| :--- | :--- | :--- |
| 汇报/宣贯（PPT 模式） | `##` 标题 + `---` 分隔 + 项目符号列表 | 一页一要点，标题即结论；每页要点不超过 5 条 |
| 方案/需求规格（Word 蓝图模式） | 多级标题（`#` / `##` / `###`）+「场景 / 规则 / 异常」 | 每个功能或场景独立成节，按场景 → 规则 → 异常展开 |
| 台账/矩阵（Excel 矩阵模式） | 标准 Markdown 完整表格 | 用于 RTM、RBAC、数据字典、接口台账；列头行头齐全，不得省略缩写、不得写「……」，不得以伪写法替代完整表格 |
| 业务流转图表（Mermaid） | Mermaid 代码块 | `graph TD` 业务流；`sequenceDiagram` 泳道时序；`stateDiagram` 状态机；图的含义以随文文字说明为准 |

## 六、方案与需求规格编写标准

1. **只写 What，不写 How（技术隔离带）**：只定义系统功能与业务要求，严禁出现数据结构、缓存、接口实现、程序异常等技术实现词汇；底层技术词汇一律功能化翻译——表 → 业务对象模型；Redis / 缓存 → 非功能性需求（性能 SLA）；API → 集成触点；异常 / 报错 → 业务控制规则（校验与拦截）。
2. **成文结构**：
   - 方案：背景与目标 → 业务流程（场景）→ 关键规则（口径 / 校验 / 权限）→ 异常处理；
   - 需求规格：功能描述 → 场景 → 规则 → 业务对象与数据要求 → 集成触点 → 非功能性需求（SLA）。
3. **排版**：按第五节「交付物排版映射协议」对应模式套版（PPT / Word 蓝图 / Excel 矩阵 / Mermaid 图表）。
4. **口径与术语**：与全库既定口径一致；关联交易术语取第四节标准术语表；科目颗粒度止于报表项目行，报表项仅允许在标准报表项后追加「—内部往来」后缀（同第三节第 3 条）。
5. **文字**：业务语言平实，严禁 AI 腔调与空话套话（同第三节第 2 条）。
6. **财务合规与准则审核要求（财务专家审核门禁）**：凡涉及内部交易、采购、销售、费用、资产与三表出表的方案与需求规格，成文后必须经独立财务专家以【资深财务与会计准则专家】身份完成准则实质初核，严禁以「排版对齐 / 编译通过 / 页面渲染正常」替代准则核验；初核结论逐条留痕：
   - **预算视角定位与 ERP 边界（先决核验尺度）**：财务专家以「预算视角的资深财务顾问」定位核验（本系统是预算系统，不是 ERP），须同时把住两条：**法理把关要准**——把握交易法律实质与准则大盘、不犯准则常识硬伤（如代采购必须定性为代理人净额法，规避集团关联交易虚增营收被审计否定）；**预算边界要牢**——绝不滑向 ERP 核算泥潭：预算根本目的是「用户最简化填表直出三表（PL/BS/CF）」；严禁记账凭证、4 位/6 位明细会计科目、发票三单匹配、账期账龄台账、往来明细销账等 ERP 执行层繁琐逻辑；科目颗粒度止于「报表项目行」、内部交易仅追加「—内部往来」；坚守预算「抓大放小、现金与大盘损益直出三表」原则、不为合规而过度精细化。核验与整改意见一律以「报表项目行 + 直出三表」为上限，超出此限的 ERP 核算类要求不予采纳；
   - **代采购净额法基准规则**：代采购在法律与商业实质上为受托代理（垫资、平价结转、只收代采服务费），一律按净额法核算——仅确认代采服务费收入（其他业务收入—内部往来）；严禁以总额法买断确认全额购销、虚增进销流水与进销差；严禁沿袭旧历史代码把代采购写成总额法；
   - **合并抵销与递延所得税**：内部往来与内部损益在集团合并层轧差清零；期末存货、资产中未实现的内部加成按准则抵销，并相应确认递延所得税资产/负债；
   - **报表科目颗粒度**：取数规则与分录严格止于报表项目行，内部交易仅允许在标准报表项后追加「—内部往来」后缀（同第 4 条）。

## 七、落地与校验

1. 方案文档改完，核对：无 localStorage 依赖、无嵌套组件拆散、术语符合第四节、排版与编写符合第五、六节。
2. 文档层（`.md`）改动不引入构建依赖；工程侧沿用既有校验 `npx tsc --noEmit`，不为文档改动新增脚本或依赖。
3. **财务专家审核门禁（硬性，见第六节第 6 条）**：凡涉及内部交易、采购、销售、费用、资产与三表出表的改动，交卷前必须由财务专家以【资深财务与会计准则专家】身份完成实质初核并逐条附核验结论——① 代采购按代理人判定、严格执行净额法（严禁总额法买断虚增购销流水）；② 合并抵销与递延所得税计提逻辑；③ 科目颗粒度止于报表项目行、内部交易仅追加「—内部往来」；④ 未沿袭旧历史代码中的不规范分录；⑤ 预算视角定位与 ERP 边界——以「预算视角的资深财务顾问」核验、不滑向 ERP 核算泥潭：预算根本目的是用户最简化填表直出三表（PL/BS/CF），严禁记账凭证、4 位/6 位明细会计科目、发票三单匹配、账期账龄台账、往来明细销账等 ERP 执行层逻辑，科目颗粒度止于报表项目行、不为合规而过度精细化。仅凭 `npx tsc --noEmit` 0 报错或页面渲染正常交卷的，视为未通过门禁、一律退回。
4. 本文件的修订逐项确认后更新；未确认不改。
